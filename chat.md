✦ 1. What are the /r/ and /s/ routes?

  They are NOT upstream leftovers. They are RepoHIVE’s own CDN / Object Storage architecture designed in hosting-2 and hosting-3 to serve pre-indexed
  repository snapshots.

  Here is what they stand for and why they exist:

  ┌────────┬──────────────┬────────────┬────────────────────────────────────────────────────────────────────────────────┬───────────────────────────────┐
  │ Route  │ Meaning      │ Mutability │ Example URL                                                                    │ Purpose                       │
  │ prefix │              │            │                                                                                │                               │
  ├────────┼──────────────┼────────────┼────────────────────────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ /s/    │ Snapshots    │ Immutable  │ /s/<snapshotId>/views/hierarchy-scale.json<br>/s/<snapshotId>/views/graph.json │ Stores precomputed views and  │
  │        │              │            │                                                                                │ index artifacts.              │
  │        │              │            │                                                                                │ Content-addressed by a        │
  │        │              │            │                                                                                │ 32-character SHA-256 hash.    │
  │        │              │            │                                                                                │ Once published, these files   │
  │        │              │            │                                                                                │ never change and are cached   │
  │        │              │            │                                                                                │ indefinitely.                 │

  Why does Next.js have app/r/ and app/s/?
   - In Production (AWS): These routes never reach Next.js. AWS CloudFront intercepts /s/* and /r/* at the CDN edge and serves them directly from an S3
     bucket (repohive-artifacts-...) using Origin Access Control (OAC). The Next.js server handles only page HTML and SSE jobs.
   - In Local Mode (npm run dev or start-local): Because you don’t have CloudFront or AWS S3 running on your machine, app/r/[...path]/route.ts and
     app/s/[...path]/route.ts act as a local mock CDN: they read the generated .br (brotli) or .json files directly from your local disk
     (.repohive-local/artifacts/) so the frontend works identically in both local and cloud environments.

  2. Upstream Dependency Audit: What remains vs. What was removed?

  We ran an audit across the repository to measure exactly what remains from upstream (repowise).

  ❌ What has been 100% removed
   - Upstream packages: packages/api-client, packages/types, and packages/ui were completely deleted.
   - External package dependencies: Dropped ~8,600 lines from package-lock.json (removed @xyflow/react, elkjs, mermaid, etc.).
   - Unused repowise features: All upstream wiki engines, chat/LLM interfaces, automated refactoring suggestions, C4 architecture builders, code health
     biomarkers, and mock test fixtures were purged.
   - Upstream APIs & mock data: The 40+ mock JSON fixtures in api-client/__fixtures__ and legacy mock REST endpoints are completely gone.

  ⚠️ What still remains from upstream
  Only three things in packages/web originate from the upstream project:
   1. The continuous-zoom canvas engine (src/features/structure-map/canvas/):
     The HTML5 2D canvas zoom-and-pan engine was derived from repowise's zoom canvas.
   2. Four basic Radix UI primitives (src/components/ui/):
     Standard shadcn-style wrappers (button, input, sheet, tooltip).
   3. The design token stylesheet (src/styles/globals.css):
     The CSS variables and theme system.

  🔎 Ghost artifacts still lingering from upstream
  While the upstream runtime code was removed, dead metadata and zombie fields are still present:
   1. Hardcoded Stub Fields in @repohive/views and ZoomNode:
     In packages/views/src/zoom-map-adapter.ts and features/structure-map/canvas/types.ts:
      - is_hotspot: false
      - is_dead: false
      - on_flow: false
      - on_flow_count: 0
     RepoHIVE does not calculate hotspots, dead code, or execution flows. These boolean flags were kept purely because the canvas types still expected them.
   2. ~150 lines of dead CSS variables in globals.css:
     Tokens like --color-refactor-extract-class, --color-refactor-break-cycle, --color-diagram-node-fill, and --color-confidence-fresh still exist in the

   3. The Google Font Lora in layout.tsx:
     An upstream serif font retained solely for the word "RepoHIVE" on the landing page header.

  Summary
  The upstream runtime is decoupled—r and s are RepoHIVE's own cloud artifact store. The remaining cleanup is to strip out the zombie fields in the canvas
  adapter and prune the dead tokens in globals.css.

✦ Coming from a Java / Spring Boot + React SPA background, it is completely understandable why this layout feels jarring.

  In traditional architectures, you have a clean physical boundary:
   * Backend: Spring Boot (Java) on port 8080 — handles REST APIs, security, JPA/database, and background tasks.
   * Frontend: React (Vite / CRA) on port 3000 — purely client-side HTML/JS/CSS that talks to Spring Boot over fetch().

  In Next.js App Router, that boundary is merged into a single framework. A page file (page.tsx) and an API route (route.ts) live side-by-side in the same
  repository running on Node.js. In RepoHIVE, someone pushed this even further by co-locating the SQLite database, scrypt auth, and background worker loop
  inside packages/web/src/server/.

  Let’s look at the feasibility of rewriting this in Java.

  ---

  Understanding What RepoHIVE Actually Consists Of

  RepoHIVE is divided into two distinct systems:

    1 ┌─────────────────────────────────────────────────────────────┐
    2 │ 1. THE CORE ENGINE & PIPELINE                               │
    3 │    • Parser: AST extraction via Tree-Sitter WASM            │
    4 │    • Core: Louvain community detection, Newman Q modularity,│
    5 │            adaptive preserve/reconstruct graph algorithms   │
    6 │    • Views: Serialization into 6 immutable JSON files       │
    7 │    • Indexer: AWS Lambda / Fargate tarball runner           │
    8 └──────────────────────────────┬──────────────────────────────┘
    9                                │ writes immutable JSON to S3 / disk
   10                                ▼
   11 ┌─────────────────────────────────────────────────────────────┐
   12 │ 2. THE APPLICATION BACKEND & VIEWER                         │
   13 │    • App Backend: Auth, SQLite DB, Quota, Job dispatch      │
   14 │    • Viewer UI: React 19, Canvas zoom engine, Sigma.js      │
   15 └─────────────────────────────────────────────────────────────┘

  Depending on what you want to rewrite, there are two distinct paths:

  ---

  Path A: Rewriting ONLY the Application Backend in Spring Boot (Very High Feasibility)

  What you would do:
   1. Keep the Engine / Indexer as-is (or run it as a CLI/worker).
   2. Replace packages/web/src/server/ with a Spring Boot application:
      * Spring Security (replacing the manual scrypt/cookie code in src/server/auth).
      * Spring Data JPA or JDBI with PostgreSQL or H2/SQLite (replacing better-sqlite3).
      * @Scheduled worker tasks (replacing run-worker.mjs).
      * Spring REST Controllers (@RestController) for /api/auth, /api/index, /api/jobs.

  5. Architectural Trade-offs

  Advantages of Moving to Spring Boot:
   1. Clean Separation of Concerns: Your React UI is purely a client-side SPA (static or Vite-based), and Spring Boot is purely an API server. No weird
      Next.js server-side vs. client-side confusion.
   2. Standard Enterprise Stack: You get connection pooling (HikariCP), standard migrations (Flyway), mature ORM/JDBC mapping, and declarative transactions
      (@Transactional).
   3. Type Safety & Maintainability: Java strongly types all API DTOs and AWS SDK models; you don't have to deal with loose JavaScript objects.
   4. Swagger / OpenAPI: You get automatic interactive API documentation via Springdoc-OpenAPI.

  The Costs & Catches:
   1. Memory Overhead on EC2:
      - Currently, RepoHIVE deploys on an AWS t4g.small (2 GB RAM).
      - Node.js Next.js uses ~120 MB RAM.
      - A standard Spring Boot JVM with the AWS SDK typically requires 300 MB – 512 MB RAM. It easily fits on a t4g.small, but you should configure
        -XX:MaxRAMPercentage=50.0.
   2. CORS & Local Routing:
      - In Next.js, the UI calls /api/... directly on the same domain without CORS.
      - With a separate Spring Boot server, you either need a reverse proxy (Caddy / Nginx) routing /api to port 8080 and / to the UI, or configure CORS
        headers in Spring Boot for local development.
   3. Deployment Changes:
      - You will need to update the Terraform EC2 deployment (deploy/box/) to install Java 21 and run a systemd unit for repohive-server.jar.

  Why is DynamoDB There? (The "Ledger")

  This is the exact piece tripping you up. DynamoDB is NOT your application database.
   - SQLite is your application database (stores user emails, passwords, who has how much quota left).
   - DynamoDB is just a shared scratchpad / distributed lock.

  Why?
  The Web Server (running on an EC2 box) and the Workers (ephemeral AWS Lambdas and Fargate containers) cannot talk to each other directly.
   - They don't share memory.
   - They don't share a filesystem.
   - Lambda spins up in 200 milliseconds, does work, and disappears.

  So how does the Web Box know what the Lambda is doing? DynamoDB.
   1. When a job starts, a row is written to DynamoDB: "Job 123 is RUNNING".
   2. As Lambda works, it writes: "Progress 50%".
   3. If someone tries to index the same repo at the same time, DynamoDB acts as a mutex/lock so you don't run two identical jobs.
   4. When Lambda finishes, it writes: "Job 123 SUCCEEDED, output is in S3 under snapshot-xyz".

  The background worker on the web box simply polls this DynamoDB table every 5 seconds to say: "Hey, did any jobs finish? Yes? Okay, let me mark it done in
  SQLite." That's it! That's all DynamoDB is used for.

  How Sizing & Serverless Actually Work

  You are spot on about Lambda vs Fargate:
   * Small & Medium Java repos (up to ~1,500 files): Processed entirely in an AWS Lambda function (10 GB RAM, fast cold start, shuts down immediately).
   * Large & Extra Large repos (like Broadleaf Commerce, Spring Framework, 30,000+ files): Lambda runs out of memory or hits the 15-minute AWS timeout
     limit. So AWS Step Functions automatically routes large repos to AWS Fargate (an on-demand Docker container with up to 32 GB RAM).

  Both Lambda and Fargate run the exact same code (packages/indexer/src/run-job.ts).

  The Journey of a Request: Step-by-Step

  Here is the exact journey from the moment a user clicks "Index Repository":

  Phase 1: User Submits a Repo
   1. User enters github.com/owner/repo and clicks submit.
   2. The Web Server receives the request:
      * Checks your user account in SQLite.
      * Asks: "Does this user have quota left today?" (Yes).
      * Deducts 1 quota point.
      * Calls AWS Step Functions: "Start an indexing job for this repo."

  Phase 2: Indexing Runs in the Cloud
   3. Step Functions launches the Lambda (or Fargate task).
   4. The worker:
      * Downloads the repo tarball from GitHub.
      * Parses the Java code into ASTs with Tree-Sitter.
      * Calculates graph cohesion and preserve/reconstruct decisions.
      * Precomputes the 6 JSON view files (the hierarchy sunburst, DSM matrix, knowledge graph, etc.).
      * Compresses them with Brotli.
      * Uploads them directly to S3 under s/<snapshot-id>/views/*.json.
      * Updates the DynamoDB table: "Job finished successfully!"

  Phase 3: The Background Worker Reconciles
   5. The web box's background worker sees the "Job finished" row in DynamoDB.
   6. It updates local SQLite: "Repository X is now indexed with snapshot ID 1234."
   7. If the job crashed due to an out-of-memory error, the worker automatically refunds the user's daily quota in SQLite.

  Phase 4: The User Views the Repo (Where CloudFront Fits In)
  Here is the key distinction about CloudFront: The web server does NOT fetch from S3 and cache to CloudFront.

  Instead, CloudFront talks directly to S3:
   1. When you open https://repohive.dev/repos/owner/repo/knowledge-graph, the browser gets the HTML page from the web box.
   2. The browser JavaScript immediately requests:
     GET https://repohive.dev/s/snapshot-1234/views/graph.json
   3. CloudFront intercepts this /s/* URL at the edge:
      * It sees /s/* and immediately routes the request to the S3 bucket, bypassing your web server completely!
      * CloudFront caches this JSON file at edge locations worldwide forever (because snapshot data is immutable).
      * Your web server never touches the heavy graph data!

  1. De-mystifying the Cryptic Names

  What is s/? (Snapshots)
  Every time a repo is indexed, the code at that specific commit is analyzed. The engine generates view files (the hierarchy, the knowledge graph, etc.).
   * Because code changes over time, they wanted historical immutability.
   * They hash the repo commit + engine version into a 32-character ID (e.g., 4e960f11a261...).
   * In S3, the folder is literally named:
    s/4e960f11a261.../views/graph.json
   * s/ just stands for "Snapshots". It's like a Git commit hash. Once written, it never changes.

  What is r/? (Repositories)
  If snapshot URLs are random hashes like s/4e960f11..., how does the frontend know which snapshot hash is the current one for google/guava?
   * Instead of putting a simple query in a database (SELECT latest_snapshot FROM repos WHERE name = 'google/guava'), they created a JSON file in S3:
    r/github.com/google/guava/latest.json
   * Inside that file is literally just:
    { "snapshotId": "4e960f11a261..." }
   * r/ just stands for "Repositories". It’s a pointer file telling the browser: "The latest snapshot for this repo is X."

  2. What are AWS Step Functions?

  Think of AWS Step Functions as a visual if/else flowchart in the cloud.

  When a user submits a Java repository:
   1. Is it a small repo (100 files)? ➔ Run AWS Lambda (cheap, fast, 30 seconds).
   2. What if it's Broadleaf Commerce (30,000 files)? ➔ Lambda crashes because of the 15-minute timeout.
   3. So Step Functions acts as an automated router:
      * "Try Lambda first."
      * "Did Lambda fail or did the pre-check say it's massive?" ➔ "Start an AWS Fargate Docker container instead (give it 32 GB RAM)."
      * "Did it succeed?" ➔ "Mark the job finished in DynamoDB."
      * "Did it fail?" ➔ "Mark it failed and trigger a refund."

  Step Functions is just AWS's way of orchestrating that retry and routing logic without writing an infinite loop on a server.

  ---

  3. Why Did They Build It This Way? (The Real Problem)

  To be fair to the original design, there was a real problem they were trying to solve:

   1. Java AST analysis is heavy:
     If a user asks to index a 1-million-line Java repo, parsing all .java files into ASTs and computing modularity graphs takes 3 minutes and 8 GB of RAM.
  If your Spring Boot / Express server tried to do that inside a standard HTTP request, the browser would time out after 30 seconds, and the server would
  crash out of memory.
   2. Traffic spike cost:
     If 10 users click "Index" at the same time, an EC2 box would melt. By offloading the indexing to serverless Lambdas/Fargate, the web server never has
  to do the heavy lifting.

  Where they went too far:
  Instead of having the Web Server act as a normal gateway (fetching the result from S3 and returning clean JSON to your React app), they bypassed the
  server completely. They forced the browser to know about S3 keys, CloudFront routing rules, s/ hashes, and r/ pointer files. That's why it feels so
  "vibe-coded" and unnatural.

  2. Concurrency: SQS FIFO vs. Step Functions (Which is Simpler?)

  You mentioned: "The concurrency can be shifted to an SQS or Step Function, whichever is simpler."

  The reason the original code had that whole DynamoDB locking nightmare was solely to enforce: "Never run more than 1 Fargate container at the same time"

  Here is the comparison between the two simplest ways to do that:

  Option A: SQS FIFO Queue (The Simplest & Most Idiomatic)
  AWS SQS FIFO has a built-in feature called MessageGroupId:
   * When a Large/XL repo is submitted, send a message to:
    repohive-jobs.fifo with MessageGroupId = "fargate-worker"
   * How AWS handles it automatically:
    SQS FIFO guarantees that messages with the same MessageGroupId are delivered strictly one at a time. It will never release the next job until the
  current container finishes and deletes the message.
   * Code required: Zero. No database tables, no lock leases, no custom timers. AWS does it in the queue hardware.

  Option B: Step Functions Native Concurrency
  If you prefer Step Functions (so you have the visual graph in AWS Console):
   * Step Functions now supports Concurrency Limits directly in workflow execution (or via a Distributed Map state with MaxConcurrency: 1).
   * When a job arrives, it enters the queue state and waits until the single slot is free.

  Verdict:
  SQS FIFO is the simplest. You drop the job onto the FIFO queue, Fargate picks it up, does the work, writes to
  repohive-artifacts/<owner>/<repo>/<snapshotId>/, and deletes the message. Done.

  RepoHIVE evolved into a full application with user accounts, logins, session cookies, daily quotas, and an EC2 box.

  Because you already have a web server and a database running, keeping that static S3 pointer file (/r/) became an unnecessary, over-engineered leftover

✦ In production, handling mutable pointers (/latest) on a CDN involves a classic distributed-systems challenge.

  Is CloudFront Cache Invalidation production-grade? Yes, but with one critical trap you must design around: Version Skew.

  Here is a breakdown of the production trade-offs and the two standard industry approaches.

  ---

  The Hidden Trap: "Version Skew" (Why Multi-File Caches Break)

  Remember that indexing a repo produces 6 different JSON view files (knowledge-graph.json, hierarchy.json, architecture.json, etc.).

  If you overwrite /latest/ in S3 and trigger a CloudFront invalidation:
   * CloudFront invalidation takes 10 to 30 seconds to reach all 450+ edge locations worldwide.
   * During that 30-second window, a user’s browser might fetch knowledge-graph.json from the new commit, but fetch hierarchy.json from an edge cache that
     hasn't invalidated yet (old commit).
   * Result: The UI breaks or shows inconsistent data because the two files don't match.

  Here are the two production-grade ways top engineering teams handle this.

  ---

  Approach 1: S3 /latest/ + CloudFront Invalidation (Good, Simple)

  If you want the /latest/ path in S3, here is how you make it strictly production-grade:

  1. Upload All Files First, Invalidate Second
  In your worker (Lambda or Fargate), never overwrite files one by one while the cache is live.
   1. Write all 6 files to S3 under s3://repohive-artifacts/<owner>/<repo>/latest/.
   2. Wait for all S3 PUT operations to complete.
   3. Call the CloudFront API:
   1    cloudFrontClient.createInvalidation(builder -> builder
   2        .distributionId(distributionId)
   3        .invalidationBatch(b -> b
   4            .paths(p -> p.quantity(1).items("/artifacts/" + owner + "/" + repo + "/latest/*"))
   5            .callerReference(String.valueOf(System.currentTimeMillis()))
   6        )
   7    );

  2. Cost & Limits:
   * Cost: AWS gives you 1,000 free invalidation paths per month. After that, it costs $0.005 per path.
   * Using the wildcard /* counts as 1 single path. So invalidating an entire repository’s latest views costs half a cent even if there are 20 files inside.
   * If you index 500 repos a day, you will pay around $60–$75/month in CloudFront invalidations. If you index 10 repos a day, it's 100% free.

  Approach 2: The Enterprise Gold Standard (Immutable S3 + DB Pointer)

  This is how companies like Netflix, GitHub, and Vercel handle assets at scale, and it is universally considered the cleanest production pattern:

   1 [S3 Bucket]  ──► ONLY stores immutable snapshot IDs (never /latest/)
   2 [Database]   ──► Stores the single string: latest_snapshot_id = "def5678"

  Why top companies do this:
   1. Zero CloudFront Invalidation Costs ($0.00):
     Because you never overwrite a file in S3, you never invalidate CloudFront. S3 files are cached at edge locations for 1 year (max-age=31536000,
  immutable).
   2. Zero Version Skew:
     Every file the browser loads is guaranteed to come from the exact same commit hash (.../def5678/...). It is mathematically impossible for files to be
  out of sync.
   3. Instant Global Updates (0 ms propagation):
     The moment the worker writes latest_snapshot_id = "def5678" to your database, the very next user immediately receives the new snapshot. No waiting 30
  seconds for CloudFront invalidations to propagate.
   4. Instant Instant Rollbacks:
     If a new index run is buggy, you don't have to re-upload files to S3. You simply run:
   1    UPDATE indexed_repositories SET snapshot_id = 'abc1234' WHERE repo = 'google/guava';
     The entire site instantly rolls back globally in under 1 millisecond.

  How Approach 2 Works in Practice with Spring Boot & React

   1. User opens: https://repohive.dev/repos/google/guava/knowledge-graph
   2. React asks Spring Boot: GET /api/repos/google/guava
      * Spring Boot queries SQLite (takes 0.5 ms).
      * Returns: { "currentSnapshot": "def5678" }
   3. React fetches from CloudFront:
     GET /artifacts/google/guava/def5678/views/knowledge-graph.json
      * CloudFront serves it from edge cache at maximum speed.

  long as you account for the wildcard invalidation in your worker.
